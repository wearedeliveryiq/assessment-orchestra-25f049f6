## 3. Approved journey

### 3.1 Snapshot and Saved Snapshot

The anonymous Snapshot uses the exact fifteen Practice questions and result boundary in DIQ-100/A. Saving requires verified registration and explicit consent. It carries the fifteen exact answers into one private 2.0 assessment draft and must not complete the assessment, create an analysis run or expose additional diagnosis.

Saved Snapshot provides:

- a polished download of the same indicative result;
- private return access;
- retention of the fifteen exact responses; and
- continuation to the paid Overview without repeating them.

### 3.2 Overview purchase

One purchase covers one verified purchaser, organisation, workspace, Saved Snapshot, linked Delivery DNA 2.0 draft, immutable analysis result and authorised Overview projection. It is not a subscription and does not include another assessment, Perspectives, Action, Knowledge Packs or TeamMates.

Access is granted only after a verified, server-processed payment success event that matches the configured offer, amount, currency, workspace and assessment. Processing is idempotent and replay-safe. Redirects, client values, failed or cancelled payments and mismatches never grant access.

The customer completes the remaining thirty questions. The resulting web and downloadable Overview must use the same authorised projection and calculation result.

### 3.3 Price and tax

The active offer is server-configured and version-pinned. Customer components must not define an independent price rule.

- Price: **£295 one-off**.
- VAT: **£0**.
- Total: **£295**.
- Disclosure: **No VAT charged — DeliveryIQ is not VAT registered.**

A price or tax change requires a new configuration version and must not rewrite historical purchases.

## 5. Overview boundary

The paid Overview provides the exact outputs and seven-section report defined in DIQ-100/A, including the overall result, five domains, fifteen capabilities, confidence and limitations, strengths, opportunities, eligible patterns, top three recommendations, bounded 30/60/90 direction, explainability and approved contextual evidence.

It does not provide customer action-state controls, owners, due dates, progress tracking, complete roadmap management, Perspectives, Knowledge Pack content, TeamMate activation or unrestricted audit trace.

Approved external evidence is contextual only. It must show its source through an asterisk or numbered reference with visible source text at the bottom of the page and must never change scoring, confidence, findings or ranking.

## 6. Cutover and history

1. Delivery DNA 2.0 is a clean replacement; there is no 1.0-to-2.0 question, response, score, result or purchase translation.
2. The founder confirmed there are no paid customers requiring access migration.
3. Before cutover, engineering must verify that no genuine paid 1.0 access has appeared. If that fact has changed, preserve it and escalate the migration decision.
4. New 1.0 checkout sessions and collection starts are disabled at the 2.0 cutover.
5. Existing 1.0 Snapshot, assessment, run, result, event and payment history remains immutable and readable under its original authority where already authorised.
6. No synthetic payment, grant, assessment or customer evidence is created.

## 7. Acceptance evidence

Engineering must demonstrate:

1. the active offer and customer copy resolve from PDR-003-004A v2.0.0;
2. exact 15/45/30 scope and exact-answer continuation;
3. saving grants no additional intelligence, payment access or analysis run;
4. all DIQ-100B fixtures execute unchanged;
5. verified payment grants exactly one scoped Overview access record;
6. redirect-only, duplicate, replayed, failed, cancelled, wrong-price, wrong-currency, wrong-workspace and wrong-assessment cases fail closed;
7. no-VAT checkout, receipt and invoice presentation is truthful;
8. unpaid and cross-tenant access is denied at data, API and UI boundaries;
9. web and download outputs reconcile to the same authorised projection;
10. contextual evidence is eligible, source-cited, caveated and calculation-neutral;
11. immutable 1.0 history is preserved and no synthetic migration occurs;
12. mobile and desktop usability, accessibility, type checking, changed-file checks, production build and hosted purchase-to-result evidence pass in an authorised test context.

Update the existing acceptance matrix and consolidated implementation report. A separate playbook or per-component report is not required.
